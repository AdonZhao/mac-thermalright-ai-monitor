# 修复显示旋转,并让设置能保存

日期:2026-07-31

## 背景

在真机上跑起来后发现 LCD 画面上下颠倒。查下来是两个独立的问题叠在一起。

### 问题一:旋转开关的名字和它的行为相反

`Sources/MacTR/Rendering/FrameRenderer.swift:35` 写的是 `if !rotate`,也就是**只有当"旋转"为假时才真的执行 180° 旋转**。于是全项目这个参数的含义都是反的:

| `rotateDisplay` | 实际画面 |
|---|---|
| `false`(默认值) | 被旋转 180° |
| `true` | 不旋转 |

因为 `AppState.rotateDisplay` 默认是 `false`,程序默认状态下就在旋转,而这台机器上的散热器朝向不需要旋转,所以看到的是颠倒的画面。

命令行也一样反:`--cli --rotate` 实际上是"不旋转"。真机验证过 —— 加上 `--rotate` 后画面才是正的。

设置窗口那个开关的说明文字写的是「显示上下反了就打开它」,这句话的实际效果是对的(默认在转,打开后不转),所以用户按提示操作不会出错。问题纯在代码内部:名字骗人,谁读都会被绕进去。

### 问题二:设置完全不保存

代码里没有任何持久化(全项目搜不到 `UserDefaults` / `@AppStorage`)。`AppState` 的设置都是普通属性,程序一重启全部回到默认值。也就是说用户在设置里把旋转关掉,下次启动又变回颠倒。

### 为什么不能自动检测朝向

`LYProtocol` 握手会解析出一个 `needsRotation` 标志,但查设备参数表 `fblProfiles`(`LYProtocol.swift:45`)可见**所有已知型号都写死为 `true`**,兜底分支也是 `true`。它是个常量,不是按具体机器测出来的,而且解析出来后从未被使用。

真正决定画面正反的是**散热器装机时的朝向**(水管朝上还是朝下),与屏幕型号无关。因此这只能是用户设置,程序无法推断。

## 目标

1. 默认状态下画面就是正的,不需要用户手动去点开关。
2. 设置改一次就记住,重启后仍然生效。
3. 代码里旋转参数的名字和行为一致。
4. 有测试挡着,这类反逻辑不会再悄悄进来。

## 不做的事

- 不保存"显示页面"这个设置。`DisplaySet` 目前只有 `systemMonitor` 一个选项,没得选,保存它没有意义。等真有第二个页面时再加。
- 不改推流、渲染、指标采集等与本问题无关的逻辑。
- 不试图自动检测朝向(见上文,做不到)。

## 设计

### 一、理顺旋转语义

改 `Sources/MacTR/Rendering/FrameRenderer.swift`:

- 第 35 行 `if !rotate` → `if rotate`。
- 第 28 行默认参数 `rotate: Bool = true` → `rotate: Bool = false`。

**为什么默认值必须一起改:** 全项目有 7 处调用 `JPEGEncoder.encode`,其中 6 处显式传 `rotate`,只有 `MacTRApp.swift:804`(`makeTestJPEG`)用默认值。默认值从 `true` 改成 `false` 后,那处的实际行为完全不变——改动前 `true` 表示不转,改动后 `false` 表示不转。若只改判断条件而不改默认值,测试图会意外变成颠倒的。

改完后:

- `AppState.rotateDisplay = false`(默认)含义变成"不旋转",正好匹配本机硬件,开箱即正。
- 设置窗口开关打开 = 真的旋转,与标签「Rotate 180°」一致。
- 命令行 `--rotate` = 真的旋转。

**注意命令行的默认行为会变。** 改动前 `--cli`(不带 `--rotate`)是旋转的,改动后变成不旋转。也就是说,以后想在命令行复现颠倒画面,得显式加 `--rotate`。这是本次有意为之的行为变更,不是回归。

### 二、设置持久化

新增 `Sources/MacTR/App/Preferences.swift`,一个职责单一的小类型,只负责三个值的读写:

- **旋转** — 布尔,默认 `false`
- **亮度** — 整数 1–10,默认 `5`
- **刷新间隔** — 浮点,默认 `0.5`

要点:

- **存储位置在构造时注入。** 正式运行用系统默认位置;测试传一个临时的独立存储区,跑完即弃,不污染用户真实设置。这是这个方案可测的关键。
- **读**:`AppState` 创建时取初始值。存储为空(首次运行)时用上面的默认值。
- **写**:在 `AppState.applySettings()` 里存一次。在**活代码**里它已是所有设置改动的唯一出口(`SettingsView` 里每个控件的 `onChange` 都调用它),所以保存只挂这一个点,不会漏。

  例外是死代码 `Sources/MacTR/UI/MenuBarView.swift`:它第 124 行也有一个亮度绑定,直接改 `state.brightness` 且**不调用** `applySettings()`。该文件全项目无人引用(App 实际使用 `MacTRApp.swift` 里的 `StatusBarController`,直接操作菜单栏图标),是早期 SwiftUI 菜单方案的残留,会被编译但永不实例化。本次一并删除,见第四节。
- **读回来的值要校验。** 亮度夹到 1–10,刷新间隔只接受 0.5 / 1.0 / 2.0 之一,超出范围回落到默认值。存储是系统级的、外部可以用 `defaults write` 直接改,也可能残留旧版本写入的值,不能假定读到的一定合法。
- 不需要旧数据迁移 —— 以前从未存过任何东西。

`AppState` 继续只管运行时状态(连接状态、帧数),不承担读写存储的职责。

### 三、边界

- **命令行调试模式**(`--cli` / `--demo` / `--benchmark`)不读保存的设置,行为完全由命令行参数决定。它们是调试工具,不应受上次在界面里点过什么影响。
- **预览窗口**不涉及旋转 —— 它直接显示渲染结果,不走推给屏幕的那条编码路径,所以永远是正的。

### 四、删除死代码 MenuBarView.swift

删掉 `Sources/MacTR/UI/MenuBarView.swift`(127 行)。

理由:它是第二个设置入口且不走保存逻辑,以后谁把它接回去,就会立刻踩到"设置改了不生效"的坑。留着一块没人跑、测试也盖不到的代码,维护成本大于价值。

安全性已确认:该文件只有一个顶层声明 `struct MenuBarView: View`,全项目无人引用,不存在别处依赖它内部的类型或辅助方法。删除后代码仍应正常构建 —— 这一点由实现阶段的构建验证兜住。真要找回,git 历史里有。

## 测试

新增测试目录 `Tests/MacTRTests/`,Package.swift 加一个测试单元依赖 `MacTR`,CI 的 `build.yml` 加一步跑测试。

### 旋转行为

造一张小图,只有左上角是亮色、其余为黑;分别以"转"和"不转"编码,再把结果解码回位图,断言亮块从左上角移到了右下角,且"不转"那张仍在左上角。

**关键细节:** 推给屏幕的图是有损压缩的,不能逐像素比对。取角落一小片区域算平均亮度再比较。

这组测试如果早就存在,问题一根本进不来。

### 设置读写

- 写入三个值再读出,值对得上。
- 存储为空时,读出的是三个默认值。
- 越界的亮度和刷新间隔被夹回合法范围。

### 已知风险与退路

项目代码全在一个"可执行程序"单元里,给可执行程序挂测试在 Swift 构建工具上偶尔会别扭。若卡住,退路是把纯计算部分(图像编码、设置读写)挪到一个独立的小单元,程序和测试都依赖它 —— 这也是更标准的做法,代价是要多挪几个文件。先试直接方式,不行再退。

## 验收标准

三条都要过:

1. 测试全绿。本机跑测试同样要带工具链环境变量(见文末备注):
   `DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer swift test`
2. 启动 App,不动任何设置,屏幕直接是正的。
3. 设置里把亮度改成 8、把旋转打开(屏幕应变为颠倒,证明开关方向正确),退出 App 再启动 —— 亮度仍是 8、仍是颠倒的。再把旋转关掉,恢复正常。

## 备注:本机构建方式

这台机器上必须用 Xcode 的工具链构建,不能用 README 里那句裸的 `swift build`:

```bash
DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer swift build -c release
```

原因:默认的命令行工具用 MacOSX27.0.sdk,该版本 SwiftUI 的 `@State` 已改为宏实现,展开需要 `libSwiftUIMacros.dylib`,而这个插件只随 Xcode 的平台目录发布。不加这个环境变量会报 `plugin for module 'SwiftUIMacros' not found`,并连带一串看似代码错误的误导性报错。

CI 用的是 GitHub 的 macOS 机器,自带完整 Xcode,不受影响。
