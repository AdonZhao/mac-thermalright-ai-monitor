## 显示旋转

**画面正反无法自动检测,只能是用户设置。**

`LYProtocol` 握手会解析出一个 `needsRotation` 标志,但设备参数表 `fblProfiles` 里**所有型号都写死为 `true`**,兜底分支也是 `true`。它是常量,不是按具体机器测出来的。真正决定画面正反的是**散热器装机时的朝向**(水管朝上还是朝下),跟屏幕型号无关。

所以别再试图从设备信息里推断朝向。那个解析出来的 `needsRotation` 目前无人使用。

**`rotate` 这个参数曾经名字和行为相反。** `JPEGEncoder.encode` 里写的是 `if !rotate`,于是 `rotate: false` 才会旋转,全部 7 处调用点的含义都是反的;而默认值 `false` 就意味着默认在旋转,所以这块屏开箱是颠倒的。现在已经理顺:**true 才旋转**。

改这个判断时**必须连默认参数一起改**。`makeTestJPEG` 吃默认值,只改判断不改默认值,USB 测试图会意外变反。

## 设置持久化

**只持久化四项**:旋转、亮度、刷新间隔、熄屏时间段。

**不存 `currentSet`** —— `DisplaySet` 枚举只有 `systemMonitor` 一个选项,没得选,存它没意义。等真有第二个页面再加。

**校验策略是刻意不对称的**:

| 值 | 越界怎么办 | 为什么 |
|---|---|---|
亮度 | **夹到 1–10** | 越界的亮度仍表达了意图,最近的合法值比默认值更接近它 |
刷新间隔 | **回落到默认** | 0.5/1.0/2.0 之外没有"最近的合法值"这回事 |
熄屏时间 | **回落到默认** | 25:00 说明它从来就不是一个时间 |

**界面的选项列表和校验用的是同一份数据。** `Preferences.refreshIntervalChoices` 既生成下拉框、又用于校验;亮度滑块的范围直接取 `Preferences.brightnessBounds`。这不是洁癖:两边分开写过一次,而一旦给下拉框加了新选项忘了改另一边,**用户选的值会在下次启动被静默重置**,不报错、不留日志 —— 正是持久化本来要消灭的那个问题。

**旧键兼容有终点。** 键名加了 `display.` 前缀,`load()` 会回落读旧的无前缀键,而 `save()` 会删掉它们 —— 所以升级后第一次改设置就完成迁移。等一两个版本后,`LegacyKey` 和 `read(_:or:)` 可以整段删掉。

## 熄屏时间段

**两端时间相同 = 不熄屏**,不是"全天熄屏"。反过来会让屏一直黑着,而用户很难想到原因是两个时间碰到了一起。界面上这种状态会显示一行提示说明它当前不生效。

**它是一个值,不是全局变量。** 渲染循环在后台线程,需要把用户当前的设置传进去;做成值也让它能在不等时钟的情况下被测试。

**时间用"从零点起的分钟数"存,不用 `Date`。** 跨午夜的窗口(18:30→09:00)必须能比较,不该把日期牵扯进来。

**界面和存储之间的转换用固定参考日,不用"今天"。** 春季跳钟那天没有 02:30,用今天去构造时间会让系统跳到 03:00 —— 存的时间会显示错,用户随手一拨就永久改掉了。测试覆盖了三个跨夏令时的时区。

## 引擎的线程规则

USB 读写**绝不能碰主线程**:主线程被阻塞会表现为系统转彩虹圈 + 键盘卡死。

`DisplayEngine` 里的状态分两类:

- **`running` / `currentSet` / `settings`** —— 多线程共享,全部在一把 `Mutex` 里。`running` 被主线程(`stop()`)、libusb 热插拔线程、睡眠唤醒处理、渲染循环四处写,而循环的 `while` 条件每帧读它。做成普通变量时这是一个编译器可以利用的竞争:它有权把读取提到循环外,那样 **`stop()` 就永远不生效**。
- **`device` / `hotplug` / `frameCount` / `lastFrameSize`** —— 只有帧循环、`connectAndRun`、`postStatus` 碰,三者都在 `usbQueue` 上,靠队列独占。

**渲染循环每帧取一次快照**,不要改成逐个字段单独加锁读 —— 那样时间段可能在一帧中途变化,读到用户从没设过的组合。

**"正在连接"是一个独立状态,不等于"没连上"。** 打开设备加握手要约 4 秒。把这段时间当成"没插屏"会让本机预览窗口在每次启动时弹出来又收回。`EngineStatus.connecting` 就是为此存在;判断该不该显示预览时,要等这次尝试**真有结果**,而不是等时钟。发送失败后等 5 秒重连那条路径也算"正在连接"。

## 设置窗口

**尺寸只在 `SettingsView` 的 `.frame` 里定义一处。** 别在 `openSettings()` 里再调 `setContentSize` —— 曾经两处各写一个不同的数,谁也不服谁。用 `NSWindow(contentViewController:)` 建的窗口本来就按内容视图尺寸来定。

**建窗口时就把 `styleMask` 传进去,不要事后重新赋值。** 在已存在的窗口上重新赋值会让 AppKit 拆掉重建窗口的框架视图,重建后的内容视图可能落在非整像素位置 —— 在 1 倍屏上表现为**标签栏文字发灰发虚**,而旁边粗体的正文依然清晰。这个 bug 存在了很久,一度被误判为显示器的问题。判断方法:满屏一致地软是显示器,单独一块软是绘制方式不一样。

**高度固定,不自动适应内容。** `TabView` 只报告当前那一页的高度,自动适应会让窗口在切换标签时跳动。

**窗口只建一个、复用,并且要被持有。** `NSWindow` 不会自己保命,关闭时可能被释放掉,而菜单项还指望能重新打开它。

## 测试

**旋转测试的图是 160×40(4:1),和真实面板同比例,而且必须断言解码后的宽高。**

只断言"哪个角最亮"是不够的:那个判断用的是被测图自身的尺寸,所以如果代码里把宽高写颠倒了,白块照样落在对角,测试照样通过。**是那两行尺寸断言在起作用,不是非方形本身。**

角落取样区的边长必须小于短边的一半,否则上下两条取样带会重叠,"哪个角最亮"就没有确定答案。

**测试用一次性的存储区**(`withThrowawayStore`),绝不碰开发者真实的设置。

## 本机构建

必须带工具链环境变量:

```bash
DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer swift build -c release
DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer swift test
DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer ./packaging/build-app.sh
```

不加会报 `plugin for module 'SwiftUIMacros' not found`,并连带一串**看起来像代码写错了**的误导性错误(`cannot find '$launchAtLogin' in scope`、`cannot assign to property: 'self' is immutable`)。原因:默认的命令行工具用较新的 SDK,那里 SwiftUI 的 `@State` 已改为宏实现,展开需要的插件只随 Xcode 的平台目录发布。

CI 用 GitHub 的 macOS 机器,自带完整 Xcode,不需要这个变量。

**验证持久化必须用打包后的 `.app`**,不能用 `.build/release/MacTR` 裸二进制 —— 裸二进制没有 bundle,设置存到哪个域名不确定,"重启后还在不在"验不准。打包版的域名是 `com.m1ngli.MacTRAI`。
